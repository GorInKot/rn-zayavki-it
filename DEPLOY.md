# Деплой на сервер

Пошаговая инструкция для переноса системы на Ubuntu-сервер, на котором уже работает портал и другие сервисы. Общее описание публикации — в [README.md](README.md#установка-на-сервер).

## 0. Вопросы к команде портала (до начала)

Без этих ответов деплой не закончить — уточните заранее:

1. Как портал передаёт личность пользователя: заголовками от обратного прокси или подписанным JWT.
2. Для заголовков — их имена, IP-адрес(а) прокси портала, кодировка кириллицы (UTF-8 или percent-encoding — поддерживаются оба).
3. Для JWT — адрес JWKS или открытый ключ, `iss`, `aud`, где лежит токен (заголовок `Authorization` или cookie), названия полей с логином, ФИО, почтой, подразделением и группами.
4. Какая группа AD даёт права администратора системы заявок.
5. Путь, по которому портал откроет вкладку (`APP_BASE_PATH`), и домен(ы) портала, с которых её можно встраивать во фрейм (`PORTAL_ORIGINS`).
6. Тот же сервер, что у портала, или отдельный — от этого зависит шаг 5 ниже.

## 1. Проверка сервера

```bash
# Docker уже может быть установлен другими сервисами
docker --version || curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # затем перелогиниться
```

Проверьте, не заняты ли порт и подсеть, которые нужны компоузу (по умолчанию порт `8080`, подсеть `172.28.0.0/24`):

```bash
sudo ss -tlnp | grep 8080
docker network ls -q | xargs -I{} docker network inspect {} --format '{{.Name}}: {{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

Если конфликт — измените `HTTP_PORT` в `.env` и/или `subnet` в `docker-compose.yml` (секция `networks.internal.ipam.config`) до первого запуска.

## 2. Перенос кода

```bash
sudo mkdir -p /opt/zayavki && sudo chown $USER /opt/zayavki
git clone <адрес-репозитория> /opt/zayavki
cd /opt/zayavki
```

Если у сервера нет доступа к git-хостингу — перенесите с локальной машины:

```bash
rsync -avz --exclude .git --exclude frontend/node_modules --exclude backend/.venv \
  ./ user@server:/opt/zayavki/
```

## 3. Конфигурация `.env`

```bash
cp .env.example .env
```

Обязательно заполнить (пример и описание каждой переменной — в самом `.env.example`):

| Переменная | Значение |
|---|---|
| `ENVIRONMENT` | `production` (по умолчанию уже так — блокирует `AUTH_MODE=dev` и отключает документацию API) |
| `POSTGRES_PASSWORD` | реальный пароль, не из примера |
| `APP_BASE_PATH` | путь, по которому портал открывает вкладку, со слешами по краям |
| `PORTAL_ORIGINS` | домен(ы) портала для `frame-ancestors` |
| `AUTH_MODE` | `headers` или `jwt` — по ответу из п. 0.1 |
| `HEADER_*` / `TRUSTED_PROXIES` | при `headers` — имена заголовков и IP прокси портала (п. 0.2) |
| `JWT_*` | при `jwt` — ключ/JWKS, `iss`, `aud`, имена claim'ов (п. 0.3) |
| `ADMIN_GROUPS` | группа AD администраторов (п. 0.4) |

## 4. Запуск

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f backend   # миграции применяются автоматически при старте
```

Демо-данные (`python -m app.seed`) в проде **не запускать** — база должна остаться пустой до реальных заявок.

## 5. Публикация через прокси портала

### Тот же сервер

Порт по умолчанию забинден только на `127.0.0.1:${HTTP_PORT}` — снаружи хоста недоступен, это ожидаемо. Прокси портала (nginx или другой) должен проксировать `APP_BASE_PATH` на `http://127.0.0.1:${HTTP_PORT}`. Пример для nginx:

```nginx
location /automation/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_set_header X-Remote-User    $remote_user_from_ad;   # заголовки, о которых договорились в п. 0.2
    proxy_set_header X-Forwarded-For  $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### Отдельный сервер

Установите `HTTP_BIND=0.0.0.0` в `.env` и обязательно закройте порт `HTTP_PORT` файрволом для всех, кроме адреса прокси портала:

```bash
sudo ufw allow from <IP-прокси-портала> to any port 8080 proto tcp
sudo ufw deny 8080/tcp
```

Цепочка передачи заголовков должна остаться: `браузер → прокси портала → nginx (frontend) → backend`. `TRUSTED_PROXIES` в `.env` должен содержать реальный IP прокси портала — иначе backend откажет в авторизации.

## 6. Проверка после запуска

- [ ] Вкладка открывается через портал по `APP_BASE_PATH`, а не напрямую по IP.
- [ ] Вход под одним реальным сотрудником проходит, ФИО и подразделение подхватились верно.
- [ ] Сотрудник из `ADMIN_GROUPS` видит реестр, дашборд и календарь; остальные — только свои заявки.
- [ ] Заявка создаётся, комментируется, у неё считается корректный срок рассмотрения.
- [ ] `docker compose logs backend` не показывает ошибок авторизации (`401`, `Запрос пришёл в обход портала`).

## 7. Производственный календарь

Сроки рассмотрения считаются с учётом праздников. 2025–2026 годы уже заполнены миграцией `0002_reference_data.py` — **сверьте с действующими постановлениями Правительства РФ о переносе выходных** перед вводом в эксплуатацию. Следующие годы администратор заполняет в разделе «Календарь» сам.

## 8. Резервное копирование

Данные — в двух Docker-томах: `pgdata` (база) и `uploads` (файлы заявок). Настройте регулярный backup обоих, например по cron:

```bash
docker compose exec -T db pg_dump -U zayavki -Fc zayavki > /backup/zayavki-$(date +%F).dump
docker run --rm -v zayavki_uploads:/data -v /backup:/backup alpine \
  tar czf /backup/uploads-$(date +%F).tgz -C /data .
```

## 9. Обновление версии

```bash
cd /opt/zayavki
git pull
docker compose up -d --build   # миграции применятся автоматически
```

Перед обновлением с изменением моделей БД — сделайте backup по п. 8.

## Диагностика частых проблем

| Симптом | Причина | Что проверить |
|---|---|---|
| `401 Запрос пришёл в обход портала` | Заголовки пришли не от адреса из `TRUSTED_PROXIES` | Реальный IP прокси портала в логах nginx vs значение в `.env` |
| `401 Неизвестный тестовый пользователь` | `AUTH_MODE=dev` осталось в проде | В проде `dev` запрещён — если ошибка есть, значит `ENVIRONMENT` не `production` |
| Вкладка не встраивается во фрейм | `PORTAL_ORIGINS` не совпадает с доменом портала | Заголовок `Content-Security-Policy` в ответе frontend |
| Кириллица в ФИО/подразделении битая | Прокси портала передаёт заголовки не в UTF-8 и не percent-encoding | `HEADER_*` значения в логах backend до `decode_header_value` |
